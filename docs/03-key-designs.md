# 03 · 关键设计与原理

本文挑出 12 个真正需要做判断的地方。每个都按 **问题 → 方案 → 代价** 写。
面试时被追问"为什么这么设计"，答案都在这。

---

## 1. 为什么自己写协议，而不用标准 RTP

**问题**：标准 RTP 有完整规范，直接用不是更省事？

**方案**：自定义 20 字节头（12 固定 + 8 扩展），只保留需要的东西。

**关键差异**：

| 差异 | 原因 |
|---|---|
| 不用 CSRC 列表，CC 恒 0 | 单 SSRC 会话用不到，省去变长解析 |
| X 位直接表示"有 8 字节扩展" | 标准扩展是 `profile+length+数据`，对固定两字段纯属冗余 |
| 只有两种 PT，不做协商 | 类型编译期定死，不需要 SDP |
| 没有 RTCP | 反向通道只有 NACK 和反馈，格式自定义 |

**代价**：**不能与标准 RTP/RTCP 端点互通**。这个项目没有互通需求，
换来的是解析代码不到 30 行、无变长字段、无分支。

**面试要点**：不要把它说成"比 RTP 更好"，要说"这是为单流低延迟场景做的裁剪"。

## 2. 把采集时间戳塞进包头

**问题**：端到端延迟只能在收端算，但收端怎么知道"这一帧是什么时候采集的"？

**方案**：每帧在源端打上 `steady_clock` 微秒时间戳（取低 32 位），随包头传过去。

**为什么可行**：两端跑在同一台机器上时 `CLOCK_MONOTONIC` 是系统级时钟，
跨进程可比。低 32 位约 71 分钟回绕一次，用**无符号差值**计算天然正确。

**代价 / 边界**：

- **跨机部署需要 PTP/NTP 同步**，否则算出来的是"包含时钟偏差"的假延迟。
  这一点在 README 的已知限制里写明了。
- 对 `udp://` 这类实时输入，本地拿到帧时上游已经缓冲过，
  所以面板的 e2e 只覆盖"本进程解码之后"的链路——启动时会打一条 warn 说明。

**这是整个项目最有价值的一个设计**：没有它，所有延迟数字都是猜的。

---

## 3. UI 只保留最新帧（覆盖式而非队列）

**问题**：解码比渲染快时，帧往哪放？

**方案**：`FrameSlot` 只存一帧，新帧覆盖旧帧，旧帧计入 `dropped`。

**为什么不用队列**：队列一旦积压，延迟会**单调增长且不可恢复**——
网络再快也追不回已经排队的旧帧。实时视频里"旧帧"没有价值。

**代价**：解码快于渲染时会丢帧。但丢帧**可统计**，不是静默消失。

**数据**：llvmpipe 软渲染下 720p 渲染约 4.76ms/帧，30fps 预算 33ms，
余量足够；1080p 时偶尔丢帧（实测 drop 0~4/秒）。

## 4. 零拷贝：mmap 缓冲直接交给上层

**问题**：V4L2 采集到的帧，怎么传给编码器而不复制？

**方案**（`v4l2_source.cpp`）：

```
DQBUF 拿到 buffer.index
  → 把 mmap 映射区包装成 shared_ptr，deleter 里 QBUF 还回驱动
  → YuvFrame 持有这个 shared_ptr
  → 编码器用完，最后一个引用释放时自动还回驱动
```

**关键点**：`Device` 对象被所有在途帧共同引用，即使 `V4l2Source` 先销毁，
已借出的帧仍能安全读取，直到最后一个帧释放才 `munmap` + `close`。

**代价**：**缓冲区数量就是最大在途帧数**。如果上层持有帧太久，
驱动没有可用缓冲会开始丢帧。所以缓冲区设了 4 个。

**不适用的情况**：非 YUV420 格式（YUYV/MJPEG）需要转换，
必须拷进帧池——这是格式不支持零拷贝的固有限制。

## 5. FU-A 重组只维护"一个正在重组的 NAL"

**问题**：多个 NAL 的分片交错到达怎么办？

**方案**：只维护一个重组缓冲。遇到新的起始片时，丢弃旧的并计数。

**为什么不做多路重组**：**按帧排序和超时策略属于抖动缓冲层**。
如果这里也缓冲堆积，两处都做会互相掩盖问题。

**代价**：极端乱序下会丢 NAL。但这个丢帧会被统计，且下一层的帧缓冲
有 60ms 窗口可以等重传。

**踩过的坑**：早期因为没做帧内重排，恢复的 NAL 被追加到帧尾，
导致一帧的 NAL 顺序错乱 → 见 [05-pitfalls.md](05-pitfalls.md) 第 3 条。

## 6. XOR FEC：简单但有限

**问题**：丢包后能不能不等重传就恢复？

**方案**：每 K=8 个包按字节异或，产出 1 个修复包。组内丢 1 个可恢复。

**三个必须的细节**：

| 细节 | 不做会怎样 |
|---|---|
| 载荷带**长度表** | 数据包长度不一致，恢复时无法精确截断，还原的包尾部残留补零字节，负载整体错位 |
| 帧边界**强制 flush** | 组跨帧时，恢复的包只能追加到后续帧，NAL 顺序错乱（实测出现 705 个 AU 而期望 600） |
| 修复包**复用数据序列号** | 给修复包独立序号会让收端误判"序列号跳了 299 次" |

**代价**：组内丢 2 个及以上无能为力。这正是 Reed-Solomon 要解决的问题。

**实测边际收益递减**：2% 丢包时贡献 +14.4dB，30% 时只剩 +2.3dB。
丢包越密，同组丢 2 个以上的概率越高。

## 7. NACK 必须等 8ms 再请求

**问题**：发现序列号缺口就立刻请求重传？

**方案**：等 8ms（重排序窗口），仍未到才发 NACK。

**为什么**：UDP 会乱序。不等就请求，会把**乱序误判成丢包**。

**实测**：600 帧的测试里，不等窗口发出 **866 次**无谓请求；加了 8ms 后降到 639 次。

**代价**：增加 8ms 延迟。这是"少发无用请求"和"早点恢复"的权衡。

**注意**：8ms 是固定值，高抖动链路上可能偏短——这是已知局限。

## 8. 抖动缓冲深度：固定还是自适应

**问题**：缓冲太浅会因抖动丢帧，太深会白白增加延迟。

**方案**：两套策略可选。

```
固定：depth = 配置值（默认 60ms）
自适应：depth = clamp(20ms, max(k × 抖动估计, RTT + 10ms), 120ms)
```

抖动估计用 **RFC 3550** 的算法（`D = (Rj - Ri) - (Sj - Si)` 做 EWMA）。

**踩过的坑（值得讲）**：k=3 的自适应**反而比固定 60ms 差 9.9dB**。

| 场景 | 固定 60ms | 自适应 k=3 |
|---|---|---|
| 无抖动 | **53.42 dB** | 43.74 dB |
| 抖动 | 37.98 dB | **42.41 dB** |

原因：**RFC 3550 的估计是 EWMA 均值，会低估峰值**。均值 2ms 的链路，
瞬时抖动可能 15ms，k=3 只给 6ms 缓冲，一溢出就丢帧。

扫了 k=3/6/8，**k=6 才与固定 60ms 持平**。所以默认 k=3，但文档里建议抖动链路用 k=6。

**这条的教学价值**：教科书算法照抄不一定好，**参数必须用自己的场景调**。

## 9. 拥塞控制：用延迟梯度，不用丢包

**问题**：什么时候该降码率？

**方案**：看**队列延迟的变化趋势**，不是看丢包。

```
单窗延迟变化 = Σ[(到达_i − 到达_{i−1}) − (发送_i − 发送_{i−1})]
  > +15ms → 过载，乘性降速
  < −15ms → 欠载，保持
  否则    → 正常，加性提速（+8%/窗口）
```

**为什么不用丢包**：等丢包发生时，队列已经堆满了。延迟梯度能在**丢包之前**发现拥塞。

**丢包作为第二信号**：>10% 直接降速；2%~10% 只暂停提速。
因为只看延迟会漏掉"缓冲区极小的链路"（还没堆积就已经丢包）。

**两个必需的补丁（都是被实验打脸后加的）**：

| 问题 | 现象 | 修复 |
|---|---|---|
| 连续下调 | 大过冲后队列要几秒排空，期间检测器仍看到正值延迟，一路降到底（1Mbit 链路被压到 200kbps 下限） | **降速冷却 250ms** |
| 单次砍太狠 | 按严重度分 4 档、一次砍 48%：1190 → 621 → 324 → 300 | **最多 2 档（≤28%）** |

**实测效果**（1.2 Mbit 链路，20 秒内容）：

| | 关闭 | 开启 |
|---|---|---|
| 接收耗时 | 27.60 s（积压 7.6s） | **20.98 s（积压约 1s）** |
| 送达 NAL | 3525 | **3663** |

**代价**：AIMD 稳定在容量的 65%–80%，这是加法提速 + 过冲即降的固有代价。

## 10. SSRC 变化 = 换流，必须重置状态

**问题**：界面里换文件或点 Restart 会新建发送端，序列号从 0 重新开始。
接收端还记着旧序列号，看到"倒退几千"会按**重传包**处理。

**现象**：画面永久冻住，而 `retransmits` 一路涨到五千多。

**方案**：发送端每次新建都生成不同 SSRC；接收端检测到 SSRC 变化时重置
流相关状态（序列号、帧缓冲、FU-A 半成品、FEC 组、待发 NACK），
但**累计统计不清零**。

**代价**：几乎没有。SSRC 只用于换流检测，不做流复用。

**这里的教训**：我第一版修复是错的——生成 SSRC 的代码放在了
`config_ = config;` 之前，生成的值立刻被覆盖成 0。**是测试把它抓出来的**
（见 [05-pitfalls.md](05-pitfalls.md) 第 10 条）。

## 11. 暂停的语义：实时源必须继续消费

**问题**：点 Pause 时，发送端要不要继续读输入？

**方案**：看源的类型。

| 源类型 | 暂停时 | 原因 |
|---|---|---|
| 文件 | **停住不读** | 暂停就该冻结，恢复时从原处继续 |
| 实时（`udp://`、摄像头） | **继续读并丢弃** | 不读的话上游缓冲会攒下几秒数据，恢复后从积压处播，画面永久落后 |

**代价**：实时源暂停期间仍然消耗解码 CPU。但这是保证"恢复时看到的是当下"的必要成本。

**发现过程**：用户报"暂停再恢复，延迟好几秒"，但日志里 264 秒最大延迟只有 152ms。
原因是**度量本身失真**——`FileSource` 给每帧打的是"本地解码时刻"，
从积压里读出的旧画面也拿到新时间戳，所以指标完全看不出滞后。

**教训**：**现象和指标矛盾时，要相信现象，然后去查指标本身。**

## 12. 单机模式为什么故意绕一圈网络

**问题**：单机演示直接解码显示不就行了？

**方案**：`--local` 模式下，进程内起一个发送端，指向自己刚绑定的端口：

```
文件 → 解码 → 重编码 → RTP-lite → UDP(127.0.0.1) → 收包 → 恢复 → 解码 → 渲染
```

**为什么值得**：中间那一圈是**真实的协议栈**。如果直接显示，
面板上的延迟、抖动、丢帧就全变成了假数据。绕一圈的代价是几毫秒回环，
换来的是所有指标可测量、可解释。

**这也解释了项目的定位**：它不是播放器，是链路。

## 附：一个反面教材（UI 缩放）

Qt 里如果一部分控件 `setFont` 了、另一部分依赖继承，缩放时必然错位：

| 控件 | 行为 |
|---|---|
| 数值列（显式 monospace） | 字号冻结在创建时刻 |
| 标题列（无显式字体） | 跟随应用字体缩放 |
| QToolButton（QToolBar 创建） | 要等下次布局才刷新 |

结果：放大窗口后标题列特别小、工具条要拖动一下才正常。

**正确做法**：缩放时把每个控件的字体都**显式重设**，
包括 `QToolBar::findChildren<QWidget*>()`。

这个坑在 UI 里连续栽了三次（面板标题列、工具条、深色背景），
本质都是同一个：**显式和继承混用**。
