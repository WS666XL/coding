# 05 · 踩坑记录

这一份是**学习价值最高**的文档。每个坑都按
**现象 → 根因 → 修法 → 教训** 写，全部是真实发生过的。

面试被问"遇到过什么难题"时，从这里挑一个讲，比泛泛而谈强得多。

---

## 1. FEC 修复包占用了序列号

**现象**：0% 丢包的测试里，接收端报告 `sequence_breaks=299`。
明明是完美链路，为什么有 299 次"序列号断裂"？

**根因**：给每个 FEC 修复包分配了独立的 RTP 序列号。
收端看到序列号跳了 299 次（每 8 个数据包插 1 个修复包），
把它当成了丢包。

**修法**：修复包**复用同组最后一个数据包的序列号**，不占独立序号空间。
修复包不是"数据"，不该参与缺口检测。

**教训**：**复用同一个编号空间之前，先问"这个编号是给谁用的"**。
修复包是冗余信息，不是新的数据单元。

---

## 2. FEC 组跨帧导致 NAL 顺序错乱

**现象**：600 帧的码流，`h264_probe` 报 `access_units=705`。

**根因**：FEC 组没有在帧边界结算。一个组跨了两帧，
组内后一帧的包丢了，恢复出来的包只能追加到**后续帧**，
导致那一帧的 NAL 顺序错乱、解码器多识别出 105 个 AU。

**修法**：每个帧边界强制 `flush()`，把未满的组也生成修复包。
这样修复包与本帧数据在同一批发出，收端能在本帧内完成恢复。

**教训**：**分组的边界必须和语义边界对齐**。FEC 组跨帧是"物理分组"与
"逻辑单元"不一致的典型后果。

---

## 3. 恢复的 NAL 被追加到帧尾

**现象**：画面偶尔出现花屏，但解码器不报错。

**根因**：NAL 按"到达顺序"存进帧缓冲。FEC/NACK 恢复的包总是**最后才到**，
所以它的 NAL 被追加到帧尾，而它原本该在中间。

**修法**：帧内按序列号重排。用 `int16_t` 差值比较以处理 uint16 回绕：

```cpp
const bool is_retransmit =
    have_sequence && (static_cast<std::int16_t>(header.sequence - last_sequence) <= 0);
```

**教训**：**"到达顺序"不等于"发送顺序"**，任何跨网络的序列都要显式重排。

---

## 4. NACK 没有等待窗口，把乱序误判成丢包

**现象**：5% 丢包的测试里，600 帧发出了 **866 次** NACK 请求。

**根因**：发现序列号缺口就立刻请求，但 UDP 会乱序——
很多"缺口"几毫秒后自己就到了。

**修法**：加 8ms 重排序窗口（`--nack-delay`），到时仍未到才请求。
请求数从 866 降到 639。

**教训**：**"没收到"和"丢了"是两件事**，中间需要时间才能区分。

---

## 5. `x264_encoder_reconfig` 改码率完全无效

**现象**：拥塞控制里码率明明降到了 300kbps，链路却始终饱和、积压 8 秒。

**根因排查**：

```
目标 2000 kbps → 实际 2128 kbps     离线编码跟随目标，正常
重配到 300 kbps 后的 40 帧: 481437 字节
重配前            40 帧: 474094 字节   ← 反而变大了
```

**`x264_encoder_reconfig` 在本机 x264 164 上修改 `rc.i_bitrate` 完全不生效。**

**更糟的是原有测试**：

```cpp
ASSERT_TRUE(encoder->set_bitrate(400, &error));
EXPECT_EQ(encoder->bitrate_kbps(), 400);   // 只验证了"自己记住了"
```

它验证的是返回值，**不是实际输出**，所以这个 bug 一直藏着。

**修法**：
1. `set_bitrate` 改为**重建编码器**（`open()` 内部先 `close()`，安全），
   代价是一次 SPS/PPS + IDR
2. 补一个真正验证效果的测试：用高熵内容比较重配前后 40 帧的实际字节数

**教训**：**测试要断言"效果"，不能只断言"返回值"**。
这是整个项目最重要的一条经验。

## 6. 彩条内容太平坦，码率控制根本没生效

**现象**：修好编码器后，码率降到 300，链路依然饱和。

**根因**：合成源是彩条画面，x264 无论目标码率设多少都只输出 **59 kbps**
（已贴 QP 上限）。**码率环控制的是一个对输出没有影响的参数。**

**验证**：

| 目标码率 | 无噪声实际输出 |
|---|---|
| 2000 kbps | **59 kbps** |
| 200 kbps（加噪声后） | 240 kbps |
| 2000 kbps（加噪声后） | 2128 kbps |

**修法**：给合成源加噪声（`--noise 60`），让内容真正需要高码率。

**教训**：**压测前先确认"被测对象真的会响应"**。
否则你测的是一个无效旋钮，得到的"自适应"是假结果。

---

## 7. 降速没有冷却，一路降到下限

**现象**：1 Mbit 链路，码率从 2000 降到 200（下限）还在继续降。

**根因**：大过冲后队列要几秒才排空，期间检测器**仍看到正值延迟**，
于是连续判过载、连续下调。

**修法**：降速后 250ms 内不许再降（`decrease_cooldown_us`），给队列排空时间。

**教训**：**控制回路要考虑"执行器的延迟"**。你的动作生效需要时间，
在这期间继续按旧观测动作会过冲。

---

## 8. 严重度分档太激进，一次砍掉 48%

**现象**：1.2 Mbit 链路上，码率已经降到 1190（几乎正好），
下一窗口仍判过载，一刀砍到 621，再砍到 324。

**根因**：按延迟严重度分 4 档，每档乘 0.85，最严重时一次乘 4 次 = 砍掉 48%。
**窗口延迟大只说明队列长，不等于"链路容量只有这么点"。**

**修法**：最多 2 档（一次 ≤28%）。

**教训**：**"观测到严重"和"该反应多剧烈"之间需要一个阻尼**。
否则系统会在工作点附近大幅振荡。

---

## 9. SSRC 自动生成被自己覆盖

**现象**：界面点 Restart 后画面冻死，`retransmits` 一路涨到 5000+。

**根因（两层）**：

1. 换文件会新建发送端，序列号从 0 开始；接收端还记着旧序列号，
   把新包全判成"倒退的重传包" → 帧永不推进。
2. 我第一版修复是"给每条流生成唯一 SSRC + 接收端检测变化后重置"，
   但**生成代码写在了 `config_ = config;` 之前**，生成的值立刻被传入的
   config（ssrc=0）覆盖。

**怎么发现的**：加了一个测试，断言"两次新建发送端 SSRC 必须不同"——**失败了**：

```
AutoGeneratesDistinctSsrcPerInstance: Failure
两次新建的发送端 SSRC 相同，换流无法被识别
```

**修法**：把生成逻辑移到赋值之后。

**教训**：**没有测试的修复等于没修**。如果只跑功能测试（画面能播），
这个 bug 会看起来像修好了。

## 10. 暂停实时源后画面滞后数秒（指标还显示正常）

**现象**：暂停再恢复，画面明显落后好几秒，但面板延迟仍是 79ms。

**根因（两个叠加）**：

1. 暂停时发送端完全不读流。实时源的上游缓冲持续堆积——
   1MB fifo 在 1.5Mbps 下能存 **5 秒**。恢复后从积压处继续播，画面永久落后。
2. **度量失真**：`FileSource` 给每帧打的时间戳是"本地解码时刻"，
   从积压里读出的旧画面也拿到新时间戳，所以指标完全看不出滞后。

**修法**：
- `CaptureSource::is_live()` 区分源类型；实时源在暂停期间**继续读取并丢弃**
- 启动时对实时源打一条 warn：面板延迟只覆盖本进程解码之后的链路

**教训**：**现象和指标矛盾时，要相信现象，然后去查指标本身。**
日志里 264 秒最大延迟只有 152ms，而用户明确看到"好几秒"——
这个矛盾本身就是线索。

## 11. `repaint()` 测出的渲染耗时差了两个数量级

**现象**：Qt 探针测出 **0.082ms/帧**（12150 fps）。对软件光栅化不可能。

**做法**：没有直接采信，加了个 `paintGL` 计数器：

```
bench widget_size= QSize(1280, 720) requested= 60 actually_painted= 1
```

`repaint()` 只触发了 **1 次**绘制，测出来的是"提交命令"的时间，
不是"渲染完成"的时间。改成事件循环驱动后才是真数据：**4.76ms/帧**。

**教训**：**任何 0.1ms 级别的渲染耗时，先怀疑测量方法。**

## 12. 录制手段干扰了被录对象

**现象**：录演示动图时，"无丢包"那一段面板显示 `BAD`、`drop 50%`、
`fps 12.8`。

**根因**：每 100ms 存一张 1280×580 的 PNG，编码要 ~15ms，
直接阻塞 UI 线程，把 30fps 拖到 12.8fps，于是解码帧大量覆盖、
`dropped` 涨到 50%，状态灯变成 BAD。

**修法**：改用 JPEG(q85)（约 3ms），帧率恢复正常。

**教训**：**观测会改变被观测系统**。做性能测试时，
采集手段本身的开销必须先量化。

## 13. 界面字号：显式和继承混用必然错位

**现象（连续三次）**：

1. 放大窗口后，右侧面板标题列（`source` / `fps`）特别小，数值列正常
2. 修完面板后，工具条（`Open file` / `Pause`）启动时字很小，
   拖动一下窗口才正常
3. 工具条背景是浅色，和深色面板割裂

**根因**：

| 控件 | 字体来源 | 缩放行为 |
|---|---|---|
| 数值列 | 创建时 `setFont(monospace)` | 字号**冻结**在创建时刻 |
| 标题列 | 依赖继承 | 跟随应用字体缩放 |
| QToolButton | QToolBar 创建时固定 | 要等下次布局才刷新 |

**修法**：缩放时把每个控件字体**显式重设**，
包括 `toolbar->findChildren<QWidget*>()`；并 `updateGeometry()` 强制重排。
给 `QToolBar` 设样式表后 Qt 会改用样式表配色，所以背景也要一起写。

**教训**：**要么全显式，要么全继承，不能混**。

## 14. WSLg 下 `x11grab` 只能抓到黑屏

**现象**：用 ffmpeg 录窗口，得到 2560×1600 全黑，只有一个鼠标指针。

**根因**：窗口由 **Wayland 合成器**渲染，`x11grab` 抓的是 XWayland 根窗口，
两者不在同一视觉空间。即使强制 `QT_QPA_PLATFORM=xcb` 也一样黑。

**修法**：让程序自己 `grabFramebuffer()` + `panel->grab()`，
视频区与面板分开抓（`QWidget::grab()` 抓不到 `QOpenGLWidget` 的内容）。

**教训**：**录屏工具依赖显示协议**。Wayland 环境下优先用应用内截图。

## 15. USB/IP 传视频：数据被截断

**现象**：`usbipd` 透传成功、`uvcvideo` 绑定 UVC 1.50，但：

```
Dequeued v4l2 buffer contains corrupted data (14778 bytes)   ← 第一帧，不完整
Dequeued v4l2 buffer contains corrupted data (64 bytes)      ← 之后全是 64~80 字节
```

**根因**：网络和驱动都排除了（TCP 3240 可达、无代理、本地虚拟网段），
剩下唯一解释是 **`vhci_hcd` 的等时传输模拟不工作**。320×240 的 MJPEG
本应 10~20KB，实际 `bytesused` 只有 64~80 字节（USB 包头的量级）。

**结论**：**WSL2 + USB/IP 不适合视频采集**，但这不等于采集代码有问题。

**后续（换到原生 Linux 后才查清）**：同样的代码放进 VMware 里的 Ubuntu 24.04，
摄像头直通给虚拟机，**MJPG 640×480@30 稳定 30fps、150 帧 `errors=0`**。
所以之前所有失败都出在 USB/IP 的等时传输上，代码本身没问题。
**教训：环境不具备时，要明确区分"没验证"和"不能用"。**

（720p 在 VM 里不稳，见下一条——那是虚拟机的 USB 带宽限制，不是同一条路的结论。）

**顺带的教训（两条）**：

- `v4l2-ctl --stream-mmap` 打印的 `<` **只表示 DQBUF 成功，不校验内容**。
  我一度据此判断"YUYV 能出帧、MJPG 不行"，是错的——两者都是残包。
- 用 `kill -9` 杀掉正在做等时传输的进程，会把 USB/IP 连接打成
  `ECONNRESET`，之后**再也恢复不了**。正确做法是 `usbipd detach`。

## 16. `$!` 拿到的不是 Windows 进程

**现象**：脚本启动 Windows 版 ffmpeg，`kill -0 $!` 立刻返回失败，
误判成"启动失败"。

**根因**：Windows 程序在 WSL 里由 `/init` 代理，`$!` 拿到的是代理进程，
`kill -0` 不能可靠反映真实状态。

**修法**：按命令行特征清理（`pkill -f "ffmpeg.exe.*udp://IP:PORT"`），
并给 Windows 进程 1 秒左右启动时间再检查存活。

**教训**：**跨边界（WSL↔Windows）的进程管理语义不同**，
不要假设 POSIX 那套一定成立。

---

## 17. 并发跑压测污染了数据

**现象**：期望 37 行的 CSV 变成 69 行。

**根因**：我误以为后台启动失败，实际两个实例都在跑，
抢占同一批端口、重复写同一份 CSV，事后无法分辨每行来自哪一次。

**修法**：`flock` 单实例锁。

**教训**：**自动化脚本必须防止自己和自己打架**。
数据一旦被污染，事后补救的成本远高于加一把锁。

## 18. 命令行参数在 `start()` 之后才设置，等于没生效

**现象**：在虚拟机上跑 `--v4l2-format yuyv --width 640 --height 480`，
日志里明明打了「优先格式=yuyv」，却仍然去解 MJPEG 并报错：

```
V4L2 设备=/dev/video0 优先格式=yuyv
[mjpeg] No JPEG data found in image
取帧失败: MJPEG 送包失败
```

**根因**：`set_preferred_format()` 的调用位置在 `source->start()` **之后**。
格式协商发生在 `start()` 内部，设置晚了自然无效，于是回落到默认优先级
（YUV420 失败 → MJPG），两个用例实际都在解 MJPEG。

**修法**：把设置移到 `start()` 之前。并且在协商完成后补一行日志，
输出实际格式名、`stride`、`sizeimage`、帧率——真机上这三个值经常和预期不同。

**教训**：**配置类接口必须在"消费它的那一步"之前调用**。
这类 bug 不会崩溃，只会让参数静默失效，比崩溃更难查。

## 19. 单帧损坏导致整条采集中断

**现象**：虚拟机上 MJPG 720p 采集，跑到第 16 帧突然失败：

```
frames=16 bytes=118046 ...
[mjpeg] overread 8
[mjpeg] No JPEG data found in image
取帧失败: MJPEG 送包失败: Invalid data found when processing input
```

而同一个设备、同一份代码，另一次运行 **150 帧全部正常**。

**根因**：UVC 驱动在启动阶段偶尔交付**不完整的 JPEG 帧**（缺 EOI 或长度异常）。
原实现把"单帧转换失败"当成致命错误直接 `return false`，整条采集就此中断。

**修法**：跳过损坏帧并计数，连续失败超过 32 次才判定格式不匹配。
计数在成功时清零。

**教训**：**实时链路里，"单次失败"和"持续失败"必须区别对待**。
一次坏帧就退出，等于把偶发故障放大成永久故障。这个 bug 平时看不出来，
只有跑够多帧才暴露——**测试要跑足够长的样本**。

## 20. 忽略 `V4L2_BUF_FLAG_ERROR`，导致解码器连锁失败 + 热循环空转

**现象**：MJPG 720p 采集跑到第 13 帧后，连续 32 帧全报
`No JPEG data found in image`，最终判定"疑似格式不匹配"。加了跳过逻辑之后变成
另一种症状：**2 秒内累计丢弃 2958 帧**，CPU 满转。

**根因（两层）**：

1. **没检查 `V4L2_BUF_FLAG_ERROR`**。规范要求带这个标志的缓冲区内容已损坏、
   不得使用。我们照旧把半帧数据喂给解码器，解码器进入异常状态，
   后续帧全部失败——看起来像"格式不对"，实际只有第一帧是坏的。
2. **跳过后是热循环**。链路不可用时驱动立刻返回错误帧，我们丢一帧就立刻 DQBUF
   下一帧，没有退避，CPU 全烧在重试上，还把真正的错误埋在日志噪音里。

**修法**：
- `DQBUF` 成功后先判错误标志，命中就 `QBUF` 回去重取并计数
- 连续 60 帧仍为错误则直接报错退出（附可操作建议：降低分辨率），不再无限重试
- 每次丢弃后退避 2ms
- 转换失败时打印 `bytesused` / `flags` / 首四字节——下次能直接判断是
  "数据缺"还是"解码器挂了"

**为什么 720p 会这样**：`dmesg` 里反复出现

```
uvcvideo 3-1:1.1: Failed to resubmit video URB (-1).
```

即 USB 等时传输提交失败。VMware 的 USB 透传撑不住 720p30 的带宽（约 30Mbps），
降到 640×480 后完全正常、稳定 30fps。

**教训**：
- **规范里那些"看起来多余"的标志位，都是有人踩过坑才加进去的**
- **重试必须有上限**。无限重试会把"偶发故障"变成"100% CPU 死循环"，
  而且日志刷屏反而掩盖了真实错误

## 附：这些坑的共性

回头看，17 个坑大致分三类：

| 类型 | 例子 | 共同点 |
|---|---|---|
| **语义错位** | FEC 包占序列号、组跨帧、到达顺序≠发送顺序 | 把"物理分组"当成了"逻辑单元" |
| **测量失真** | repaint 计数、PNG 阻塞 UI、时间戳打本地时刻、`<` 不校验内容 | **观测手段本身改变了结果** |
| **测试不严** | 只验证返回值、只测无噪声内容、修复没被测试覆盖 | 断言的是"没崩"，不是"对了" |

第二类最危险——**它会让你在错误的数据上做出正确的推理**。
这个项目里我连续栽了四次，所以现在做任何优化前，
第一件事都是先确认度量是真的。
