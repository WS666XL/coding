# 01 · 系统全景

## 1. 它是什么，不是什么

**是**：一条完整的低延迟视频传输链路——把画面从"产生"送到"显示"，
中间的所有环节（编码、打包、传输、抗丢包、缓冲、解码、渲染）都是自己实现的。

**不是**：播放器。播放器直接读文件渲染；这个项目**绕了一圈网络**，
所以延迟、丢包、抖动都是真实存在的，也必须被真实处理。

这个区别决定了整个项目的价值：**90% 的代码在处理"网络不完美"这件事**。

## 2. 能力矩阵

| 能做 | 不能做 |
|---|---|
| 任意视频文件作为输入（mp4/mkv/avi/mov/flv/webm/ts） | ❌ 音频 |
| 合成测试源（彩条 + 帧号 + 可选噪声） | ❌ 录制到文件（只在命令行落盘） |
| V4L2 摄像头（YUV420 / YUYV / MJPEG，已在虚拟机实机验证） | ❌ 加密（明文 UDP） |
| 网络流作为输入（`udp://` `rtp://`） | ❌ 多路流并发 |
| 跨机传输 + FEC + NACK 重传 | ❌ Windows / macOS |
| 拥塞控制（延迟梯度 + AIMD） | ❌ 与标准 RTP/RTCP 互通 |
| 抖动缓冲（固定 / 自适应） | ❌ 裸机实机验证（只在 VM 里跑过） |

## 3. 七个模块与依赖方向

```
        ┌──────────────────────────────────────────┐
        │  ui       Qt6 界面 / GL 渲染 / 指标面板    │
        └───────────────┬──────────────────────────┘
        ┌───────────────┴──────────┐
        │  app   两个命令行程序      │
        └───────────────┬──────────┘
        ┌───────────────┴──────────────────────────┐
        │  transport   发送器 / 接收流水线 / UDP     │
        └───────────────┬──────────────────────────┘
        ┌───────────────┴──────────┐   ┌───────────┴─────────┐
        │  protocol  协议与算法     │   │  codec  x264/FFmpeg │
        └───────────────┬──────────┘   └───────────┬─────────┘
        ┌───────────────┴──────────┐   ┌───────────┴─────────┐
        │  capture   采集抽象       │   │  common  基础组件    │
        └───────────────┬──────────┘   └───────────┬─────────┘
                        └──────────┬───────────────┘
                             common（谁都可以依赖）
```

依赖只能向下，`protocol` 不知道 `transport` 存在，`transport` 不知道 Qt 存在。
好处：**协议层可以脱离网络单测**——这是 198 个测试里最扎实的那部分的基础。

## 4. 一帧的完整旅程

这是理解本项目最重要的一张表。每一行都能落到具体文件和函数。

| # | 步骤 | 代码位置 | 关键点 |
|---|---|---|---|
| 1 | 采集出 YUV 帧 | `capture/*_source.cpp` → `next_frame()` | 统一成 I420 + 采集时间戳 |
| 2 | 编码 | `codec/encoder.cpp` → `encode()` | x264 zerolatency，输出 Annex-B |
| 3 | 切 NAL | `protocol/h264_fragmenter.cpp` → `split_annexb()` | 按起始码切，兼容 3/4 字节 |
| 4 | 分片 | 同上 → `fragment_nal()` | ≤1200 字节单包，否则 FU-A |
| 5 | 加协议头 | `protocol/rtp_lite.cpp` → `serialize_rtp_lite()` | 20 字节，含帧号与采集时刻 |
| 6 | 攒 FEC 组 | `protocol/fec_xor.cpp` → `add()` | 每 8 个包出 1 个修复包 |
| 7 | 发送 | `transport/stream_sender.cpp` → `send_frame()` | `sendmmsg` 批量发 |
| 8 | 收包 | `transport/stream_receiver.cpp` → `poll()` | 一次 poll 收一批 |
| 9 | FEC 恢复 | 同上 → `recover_with()` | 组内丢 1 个可救 |
| 10 | 去重 | 同上 → `seen_sequences` | FEC 与 NACK 可能重复交付同一包 |
| 11 | FU-A 重组 | `protocol/h264_fragmenter.cpp` → `feed()` | 只维护一个正在重组的 NAL |
| 12 | 帧缓冲 | `stream_receiver.cpp` → `frame_bufs` | 收齐 / 到期 / 超限 三者触发交付 |
| 13 | 解码 | `codec/decoder.cpp` → `feed_nal()` | 有约 1 帧固有延迟 |
| 14 | 渲染 | `ui/video_widget.cpp` → `set_frame()` | 三张 GL_R8 纹理 + 片元着色器 |

**延迟就是在第 12 步和第 13 步产生的**：60ms 抖动缓冲 + 33ms 解码固有延迟。
加起来约 110ms，这是设计上的取舍，不是性能问题。

## 5. 三种运行模式

### 5.1 单机播放文件（最常用）

```bash
./scripts/demo.sh 你的视频.mp4
```

一个进程，一个窗口：

```
文件 → 解码 → 重编码 → RTP-lite → UDP(127.0.0.1:随机端口) → 收包 → 解码 → 渲染
```

**为什么要绕一圈**：因为中间的协议栈是真的，所以面板上的延迟/丢包指标是真的。
如果直接把解码结果显示出来，就只是个播放器。

### 5.2 摄像头（Windows 侧采集）

```bash
./scripts/camera.sh
```

```
Windows ffmpeg 采集摄像头 → H.264/TS → UDP → 本程序（同 5.1 的后半段）
```

WSL2 拿不到 `/dev/video0`，所以采集放在 Windows 侧。
**这条路径不经过本项目的 V4L2 代码**，但链路后半段完全一样。

### 5.3 跨机（真实用途）

```bash
# A 机发送
./build/src/app/lowlat_sender --source file --input a.mp4 --loop \
    --dest 192.168.1.50:5000 --fec --cc

# B 机接收
./build/src/app/lowlat_receiver --bind 0.0.0.0:5000 --nack --feedback
```

### 5.4 离线校验（开发用）

```bash
./build/src/ui/lowlat_ui --input out/recv.h264 --frame 300 --dump /tmp/f.png
```

不开窗口，把指定帧渲染成 PNG，用于和 ffmpeg 做像素级比对。

## 6. 线程模型

只有三个线程，边界很清楚：

| 线程 | 职责 | 明确不做什么 |
|---|---|---|
| 采集/编码/发送线程（`LocalSender::run` 或 `sender_main`） | 取帧 → 编码 → 打包 → 发送 | 不碰 socket 接收 |
| 收包/解码线程（`ReceiverThread::run`） | `poll()` → 重组 → 解码 | 不碰 UI |
| UI 线程 | 从帧槽取成品帧 → 上传纹理 → 绘制 | **不碰 socket、不碰解码器** |

跨线程只有一处交接：`ui/frame_slot.hpp`。

```cpp
// 覆盖式，不是队列
void put(DecodedFrame frame);   // 新帧覆盖旧帧，旧帧计入 dropped
bool take(DecodedFrame* out);   // UI 线程取走
```

**为什么是覆盖而不是排队**：队列一旦积压，延迟会单调增长且不可恢复
（网络再快也追不回已经排队的旧帧）。覆盖式天然有界，代价是解码快于渲染时丢帧——
但丢帧**可统计**，不是静默消失。

**验证**：ThreadSanitizer 跑全量测试，0 个数据竞争。

## 7. 关键常量

改这些值会直接改变行为，值得记住：

| 常量 | 默认值 | 位置 | 影响 |
|---|---|---|---|
| 帧保持窗口 | **60 ms** | `--hold` | 端到端延迟的主导项；降到 20ms 可省 40ms，代价是重传来不及 |
| 单包上限 | **1200 B** | `--max-payload` | 加 20 字节头 = 1220，留足 MTU 余量 |
| FEC 组大小 | **8** | `--fec-group` | 每 8 包 +1 修复包 = 12.5% 带宽开销 |
| 重传缓存 | **1024 包** | `retransmit_capacity` | 超出后 NACK 无法满足 |
| NACK 等待窗口 | **8 ms** | `--nack-delay` | 太短会把乱序误判成丢包（实测 866 次误判） |
| 反馈周期 | **300 ms** | `feedback_interval_ms` | 拥塞控制的采样间隔 |
| 帧缓冲上限 | **8 帧** | `kMaxBufferedFrames` | 超限强制交付最旧帧，防止内存膨胀 |
| 码率范围 | 300–4000 kbps | `--min/max-bitrate` | 拥塞控制的上下界 |

## 8. 标识符与端口

| 项 | 值 | 说明 |
|---|---|---|
| 版本号 | 2 | RTP-lite 头里的 V 字段 |
| PT=96 | H.264 载荷 | |
| PT=97 | FEC 修复包 | |
| 控制报文 `0x01` | NACK | |
| 控制报文 `0x02` | Feedback | |
| SSRC | 自动生成 | 每次新建发送端不同，用于换流检测 |

默认端口习惯用 5000，单机模式用 0（内核分配随机端口，避免和系统里其他进程冲突）。

## 9. 一句话总结

> 这是一个"把协议栈自己写一遍"的项目。功能上它能把视频从 A 传到 B；
> 价值上，它让每一个环节的延迟和代价都可以被测量、被解释。
