# 面试问答

本文按"被问到的顺序"组织。每个答案都对应代码或实测数据，**引用的数字都能在
`docs/benchmark.md` 与 `docs/bench-raw.csv` 里核到**。

---

## 0. 先用一句话说清楚这个项目

> 用 C++17 从零实现了一条低延迟视频传输链路：摄像头/文件 → x264 编码 →
> 自定义 RTP-lite 协议 → UDP → XOR FEC + NACK 恢复 → 抖动缓冲 → 解码 →
> OpenGL 渲染，端到端延迟 110ms，5% 丢包下画质 60.97dB、NAL 送达率 99.7%。

**不要说**"做了一个视频播放器"。播放器不传数据，这个项目 90% 的代码在传。

---

## 1. 为什么不直接用 WebRTC / FFmpeg 的现成方案？

三个层面：

1. **学习目的**：WebRTC 把拥塞控制、FEC、抖动缓冲全封装了，调它的 API
   学不到协议细节。我想自己写一遍 RTP 分片、FEC 组、NACK 调度。
2. **可控性**：需要把"采集时间戳"塞进包头来精确测量端到端延迟，标准 RTP
   要靠 RTCP SR 换算，链路更长、更难调试。
3. **代价是明确的**：不能与标准 RTCP 端点互通、没有加密、只支持单流。
   这些写在 README 的"已知限制"里。

如果目标是**生产可用**，我应该用 WebRTC；如果目标是**搞懂原理**，自己写一遍
是对的。这个项目是后者。

## 2. 一条帧从采集到上屏经过哪些步骤？

```
采集(1) → 编码(2) → 切 NAL + FU-A 分片(3) → 加 RTP-lite 头(4)
→ XOR FEC 组(5) → UDP 发送(6) → 收包 + 解析(7) → FEC 恢复(8)
→ 去重(9) → FU-A 重组(10) → 帧缓冲(11) → 解码(12) → 纹理上传(13) → 渲染(14)
```

**能画出这张图并说清每步的数据结构，基本就证明你真做过。**

几个关键点：

- **第 3 步**：NAL 超过 1200 字节就 FU-A 分片，首片 S=1、末片 E=1
- **第 5 步**：每 8 个包生成 1 个修复包，**帧边界强制 flush**（否则组跨帧，
  恢复出的包会追加到后续帧，NAL 顺序错乱）
- **第 9 步**：`seen_sequences` 去重，因为 FEC 恢复的包和 NACK 重传的包可能
  是同一个（早期 bug：FEC+NACK 同时开时 NAL 数比预期多）
- **第 11 步**：帧收齐、或保持窗口到期、或缓冲超限，三者任一触发交付

## 3. 丢包怎么处理的？FEC 和 NACK 怎么分工？

**两个机制解决不同场景，必须配合**：

| | XOR FEC | NACK 重传 |
|---|---|---|
| 原理 | 前向纠错，发冗余包 | 反馈重传 |
| 延迟 | **0**（收到就能恢复） | **≥ 1 RTT + 8ms 等待** |
| 能力 | 组内丢 **1** 个可恢复 | 能恢复任意丢包，只要缓存还在 |
| 开销 | **+12.5%** 带宽（常驻） | 只在丢包时产生 |
| 失效场景 | 组内丢 ≥2 个 | 缓存已淘汰（1024 包外）、对端已退出 |

**分工逻辑**：

- FEC 处理**零星的、单发的**丢包，不需要等重传，不增加延迟
- NACK 处理**成簇的**丢包（FEC 无能为力）和 FEC 组已过期的包
- 两者叠加：FEC 先扛，扛不住再由 NACK 补

**实测数据支撑这个分工**：

| 丢包率 | 无恢复 | 仅 FEC | FEC + NACK |
|---|---|---|---|
| 2% | 47.15 dB | 61.56 | **inf** |
| 5% | 40.26 dB | 48.32 | **60.97** |
| 20% | 34.18 dB | 35.80 | **39.98** |
| 30% | 30.73 dB | 33.07 | **35.54** |

**注意 FEC 的边际收益在下降**：2% 时贡献 +14.4dB，30% 时只剩 +2.3dB。
因为丢包越密，同一组里丢 2 个以上的概率越高，XOR 就废了。

`inf` 的含义是**恢复后的码流与参考流逐字节相同**，不是"看起来差不多"。

## 4. 为什么 FEC 用 XOR 而不是 Reed-Solomon？

**XOR 的硬限制**：一组 K 个包只能恢复 1 个丢包。丢 2 个就无解。

**为什么还选它**：

1. **编码成本**：XOR 是 `memxor`，比 RS 的伽罗瓦域矩阵运算快一到两个数量级
2. **解码成本**：恢复一个包就是"其余包全异或一遍"，O(K)，无矩阵求逆
3. **实现复杂度**：RS 需要 `gf256` 乘法表、矩阵求逆、错误定位，代码量至少 5 倍
4. **实际效果够用**：随机丢包（`netem loss`）下，5% 丢包时组内丢 2 个的概率
   约 0.7%，XOR 已经能救回 98.9% 的 NAL

**如果要做 RS，触发条件是**：突发丢包（成簇丢）或者高丢包率场景。
这是我列在"后期加分项"里的，没做。

面试如果被追问"为什么不做 RS"，答**"知道它能解决什么问题，但当前数据下
ROI 不够，明确知道这是取舍"**比硬说 RS 没必要更好。

## 5. 110ms 延迟是怎么构成的？能压到多少？

实测拆解（1280×720，UI 上屏时刻）：

| 环节 | 耗时 | 能否压缩 |
|---|---|---|
| 帧保持窗口 | **60 ms** | ✅ 配置项，可降到 20ms |
| 收包 + 重组 + FEC/NACK | ~8 ms | ❌ 已经很低 |
| **H.264 解码器固有延迟** | **~33 ms** | ❌ 编码格式决定 |
| UI 取帧等待 | 8.5 ms | ⚠️ 定时器粒度，可降到 4ms |
| **合计** | **~110 ms** | |

**33ms 是什么**：H.264 解码器要用"下一个 AU 的时间戳"来判断当前帧的
`PicOrderCnt`（B 帧重排需要），所以 `send_packet` 之后不会立刻出帧，
必须再喂一帧才吐出上一帧。**这是格式固有的，不是代码 bug**。

验证方法：headless 收端（NAL 落盘时刻）p50 = 68ms，UI（上屏时刻）p50 = 110ms，
差值 42ms ≈ 33ms 解码 + 8.5ms 取帧。两者独立测量能对上，说明拆解是对的。

**能压到多少**：把窗口从 60ms 降到 20ms，能到 **70ms 左右**。
实测代价是 PSNR 从 53.42dB 掉到 43.74dB（-9.7dB），因为重传来不及。
**这就是低延迟和抗丢包的真实权衡**，不是调参能两全的。

## 6. 抖动缓冲深度怎么定的？为什么不用固定值？

固定 60ms 在无抖动链路上是纯浪费——40ms 白等。

**自适应策略**（`BufferDepthPolicy`）：

```
depth = clamp(下限 20ms, max(k × 抖动估计, RTT + 10ms), 上限 120ms)
```

- 抖动估计用 **RFC 3550** 的算法：`D = (Rj - Ri) - (Sj - Si)` 做 EWMA
- `RTT + 10ms` 保证重传来得及（请求 8ms + 往返）
- k 默认 3.0，可调

**踩过的坑（值得讲）**：k=3 时自适应反而比固定 60ms 差 9.9 dB。

```
无抖动: 固定 53.42dB / 自适应 43.74dB
抖动:   固定 37.98dB / 自适应 42.41dB
```

原因：**RFC 3550 的抖动估计是 EWMA 均值，会低估峰值**。均值 2ms 的链路，
瞬时抖动可能 15ms，k=3 只给 6ms 缓冲，一溢出就丢帧。

扫了 k = 3/6/8，**k=6 才与固定 60ms 持平**，k=8 开始过度保守。
所以现在默认 k=3 但文档里建议抖动链路用 k=6——**这是实测调出来的，不是拍脑袋**。

## 7. 拥塞控制怎么做的？

**简化版 GCC（延迟梯度）+ AIMD**。

### 核心信号是延迟梯度，不是丢包

```
单窗延迟变化 = Σ[(到达_i − 到达_{i−1}) − (发送_i − 发送_{i−1})]
```

- `> +15ms` → 过载（队列在涨）→ 乘性降速
- `< −15ms` → 欠载（队列在排空）→ 保持不变
- 否则 → 正常 → 加性提速

**为什么不用丢包做信号**：等丢包发生时，队列已经堆满了。延迟梯度能在
**丢包之前**就发现拥塞。

### 丢包作为第二信号

超过 10% 直接降速；2%~10% 之间只暂停提速。因为只看延迟会漏掉"缓冲区极小的
链路"（还没堆积就已经丢包）。

### 实测效果（1.2 Mbit 链路，20 秒内容）

| | 关闭拥塞控制 | 开启 |
|---|---|---|
| 接收耗时 | 27.60 s | **20.98 s** |
| 累积排队 | 7.6 s | **≈1 s** |
| 送达 NAL | 3525 | **3663** |
| 末窗队列延迟 | 持续增长 | **0.5~1.6 ms** |

码率轨迹是标准 AIMD 锯齿：`1400 → 1190 → 860 → 621 → 324 → 350 → ... → 882 → 688`，
最终在 **800–950 kbps** 摆动（约链路容量的 65%–80%）。

### 两个必须的补丁（都是被实验打脸后加的）

| 问题 | 现象 | 修复 |
|---|---|---|
| 连续下调 | 大过冲后队列要几秒排空，期间仍看到正值延迟，一路降到底（1 Mbit 链路被压到 200 kbps 下限） | 降速冷却 250ms |
| 单次砍太狠 | 按严重度分 4 档、一次砍 48%：1190 → 621 → 324 → 300 | 最多 2 档（≤28%） |

**70% 的链路利用率是 AIMD 的固有代价**，不是缺陷。要更高利用率就得承受
更频繁的排队。

## 8. 线程模型是什么？

**三个线程，边界清晰**：

| 线程 | 职责 | 不做什么 |
|---|---|---|
| 采集/编码/发送线程 | 取帧 → 编码 → 分片 → 发送 | 不碰 socket 接收 |
| 收包/解码线程 | `poll()` → 重组 → 解码 | 不碰 UI |
| UI 线程 | 从帧槽取成品帧 → 上传纹理 → 绘制 | **不碰 socket、不碰解码器** |

**跨线程只用一个 `FrameSlot`**（有界最新帧槽，覆盖式）。

**为什么是覆盖式而不是队列**：队列一旦积压，延迟会单调增长且不可恢复。
覆盖式天然有界，代价是解码快于渲染时丢帧——但丢帧**可统计**（`dropped()`）。

**验证方式**：ThreadSanitizer 跑全量测试，**0 个数据竞争**。

---

## 9. 内存是怎么管的？有没有拷贝？

**帧缓冲用池化 + 引用计数**（`FramePool` + `shared_ptr`）：

- 采集申请 → 编码用完归还 → 池里复用，避免每帧 `malloc`
- 跨线程传递靠 `shared_ptr` 保证生命周期

**零拷贝点**：

1. **V4L2 MMAP**：内核缓冲直接映射到用户空间，不需要 `read()` 拷一次
2. **纹理上传**：`stride == width` 时直接 `glTexSubImage2D`，不经过中间缓冲
3. **解码输出**：`av_frame_move_ref` 搬引用，不复制像素

**有拷贝的地方（刻意的）**：

- `stride != width` 时要逐行拷成紧凑缓冲（`GL_UNPACK_ROW_LENGTH` 不可靠）
- FU-A 分片要拷进新缓冲（要加 RTP 头）

**内存安全验证**：valgrind 跑收发两端，发送端 `All heap blocks were freed`，
接收端 0 泄漏。

## 10. 这些数字是怎么测出来的？

**这是最容易被追问、也最容易露馅的地方**，必须能说清楚。

**工具**：`scripts/bench.sh`，自动跑 6 档丢包 × 3 种恢复策略 × N 次重复。

**关键设计**：

1. **跑在独立 netns 里**（`unshare -rn`），`tc netem` 只影响这个隔离环境
2. **用 headless 接收端，不用 Qt 界面**——界面走 llvmpipe 软件渲染，
   会引入不可复现的抖动。压测只测传输层
3. **参考码流由本项目自己的编码器生成**，保证参数一致；用 ffmpeg 生成会
   让 PSNR 失去意义
4. **加了单实例锁**（`flock`）——有一次两个实例并发跑，抢占同一批端口、
   重复写同一份 CSV，数据事后无法分辨来源

**PSNR 口径**：收端落盘的 `.h264` 与参考流逐帧比对。

**已知弱点（主动说）**：

- **每档只有 2 次重复**，方差较大
- **PSNR 是逐帧对齐的**——如果某次恰好丢了第一帧，整段帧序错位，PSNR 会被
  严重低估。实测出现过 `2% 无恢复 33.98dB` 反而低于 `5% 45.82dB` 的异常值
- 只测了单向丢包（`netem` 在 `lo` 上双向生效，比真实单向更严苛）

## 11. 印象最深的 bug 是哪个？

**三个层次递进的，都能讲**：

### ① 逻辑 bug：FEC 恢复的 NAL 被追加到帧尾

**现象**：600 帧的码流，`h264_probe` 报 `access_units=705`。

**原因**：NAL 按"收到的顺序"存放，而恢复的包总是最后才到。

**修复**：帧内按 `int16_t` 序列号差值重排。用 `int16_t` 是为了处理 uint16 回绕。

### ② 测量 bug：repaint() 测出的渲染耗时是假的

**现象**：Qt 探针测出 `0.082ms/帧`（12150 fps）——对软件光栅化不可能。

**做法**：没直接采信，加了个 `paintGL` 计数器：

```
requested=60  actually_painted=1
```

`repaint()` 只触发 1 次绘制，测出来的是"提交命令"的时间，偏差两个数量级。
改成事件循环驱动后才是真数据：**4.76ms/帧**。

**结论：任何 0.1ms 级别的渲染耗时，先怀疑测量方法。**

### ③ 测试自己写错的 bug：SSRC 修复被测试打脸

界面点 Restart 后画面冻死。修法是"给每条流唯一 SSRC，接收端检测变化后重置"。

改完我加了个测试验证"两次新建发送端 SSRC 必须不同"，**结果失败**：

```
AutoGeneratesDistinctSsrcPerInstance: Failure
```

原因：生成 SSRC 的代码写在了 `config_ = config;` **之前**，生成后立刻被
传入的 config（ssrc=0）覆盖。**如果不写这个测试，这个"修复"会看起来像成功，
实际仍会冻屏。**

## 12. 如果重做，你会改什么？

1. **采集时间戳换成像 `CLOCK_MONOTONIC_RAW` 并跨机同步**，否则跨机测不了延迟
2. **FEC 上 Reed-Solomon**（或至少加"组内丢 2 也尝试恢复"的 LDPC 方案）
3. **NACK 等待窗口自适应**，现在固定 8ms，高抖动链路偏短
4. **色彩矩阵从 SPS VUI 读**，现在硬编码 BT.601，接真实 720p 源（应走 BT.709）会偏色
5. **拆包**：现在 `.deb` 里命令行工具被迫依赖 Qt6，应该拆成两个包

## 13. 这个项目有什么不足？（必须能主动说）

**主动承认边界比被问出来强**：

| 不足 | 具体到什么程度 |
|---|---|
| **V4L2 没在实机跑通** | 8 个 ioctl 全实现，格式协商支持 YUV420/YUYV/MJPEG（真实 UVC 只给后两种），转换逻辑有 11 个单测。但实机卡在环境：WSL2 只能走 `usbipd` 透传，透传成功、`uvcvideo` 绑定 UVC 1.50，可是**数据在等时传输中被截断**——320×240 一帧应有 10~20 KB，实际 `bytesused` 只有 64~80 字节，ffmpeg 直接报 `corrupted data`。截断发生在驱动层之下，换格式救不回来，**WSL2 + USB/IP 不适合视频采集** |
| **没有音频** | 纯视频 |
| **没有加密** | 明文 UDP |
| **只支持单流** | SSRC 只用于换流检测，不做流复用 |
| **拥塞控制只测了 loopback** | `netem rate` 限速，没有真实跨机链路；单流、无交叉流量 |
| **色彩矩阵硬编码** | BT.601，接真实 1080p 源会偏色 |
| **压测重复次数少** | 每档 2 次，PSNR 方差大 |

**反面教材**：不要说"支持摄像头实时采集"——没在真机上跑通过。
正确的说法是"实现 V4L2 MMAP 零拷贝采集路径（WSL2 无设备，仅编译验证）"。

## 14. 追问陷阱：这些问题的浅答案会翻车

### ① "FEC 开销多少？" 
只说 12.5% 不够。要能说：**这是常驻开销，无论有没有丢包都要付**。
所以低丢包链路（<1%）开 FEC 是净亏，应该有开关策略——目前是人工开关，没做自适应。

### ② "为什么 33ms 解码延迟压不掉？"
说"解码器慢"是错的。真相是 **H.264 需要下一个 AU 判定 `PicOrderCnt`**，
是格式决定的。除非用无重排编码（`bframes=0` 已经做了）或者换编码格式。

### ③ "延迟 110ms 算低吗？"
**不算**。专业级（如 NDI、WebRTC 局域网）能到 40–60ms。
诚实的说法是：**110ms 里有 60ms 是我们自己的缓冲**，压到 20ms 就能到 70ms，
代价是抗丢包能力下降。这是取舍，不是做不到。

### ④ "PSNR 60dB 是什么水平？"
PSNR 高不代表画质好——**它对"整体偏移"敏感，对"局部块效应"不敏感**。
60dB 说明**码流与参考流几乎逐字节相同**（我们的 `inf` 就是这个意思），
不是"画质提升了 20dB"。这个指标在这里的作用是**验证恢复机制是否完整**，
不是评价观感。

### ⑤ "为什么不用 UDP 的拥塞控制？"
UDP 本身没有拥塞控制，这正是需要应用层做的原因。QUIC 有，但我们没做，
所以**这个项目在公网上是不友好的**（会抢带宽）。这是已知缺陷，不是疏忽。

## 15. 一句话收尾（如果被问"你从这个项目学到什么"）

> 最大的收获不是协议本身，而是**学会了怀疑自己的测量**。
> 那个 0.082ms 的渲染基准、那个"看起来修好了"的 SSRC bug，
> 都是先被数据打脸、才发现问题的。
> 现在我做任何优化前，第一件事是先确认度量是真的。
