# 压测数据与方法

本文记录项目里所有可复现的实测数据。所有数字都来自本仓库的脚本与程序，没有估算值。

## 测试环境

| 项 | 值 |
|---|---|
| 系统 | Ubuntu 24.04 on WSL2（内核 6.18.40.1-microsoft-standard-WSL2） |
| CPU | 与 IDE 共享的宿主 CPU |
| 编码 | libx264，`veryfast` + `zerolatency` + `bframes=0` + `sliced-threads=1`，2000 kbps，720p@30fps |
| 网络 | `ip netns` + `tc netem` 加在 `lo` 上 |
| GL | llvmpipe（Mesa 25.2.8，软件光栅化） |

## 实验一：丢包档位扫描

### 方法

```bash
./scripts/bench.sh
```

脚本的行为：

1. 用 `unshare -rn` 把自身重新拉起在独立网络命名空间里，`tc netem` 只作用于 `lo`
2. 每个档位启动 headless 接收端（落盘 `.h264`），再启动发送端，发送 300 帧后比对
3. 参考码流由**本项目自己的编码器**生成（`--no-realtime`），保证编码参数与发送端完全一致
4. 每档重复 2 次取平均

**为什么用 headless 接收端而不是 Qt 界面**：界面渲染走 llvmpipe，会引入不可复现的抖动；压测必须只测传输层。界面链路单独测（见实验三）。

**为什么参考流必须自己生成**：用 `ffmpeg` 生成参考流时编码参数（preset、码率控制、slice 策略）都不同，PSNR 会失去可比性。

### 结果：PSNR（dB，相对参考流）

| 丢包率 | 无恢复 | 仅 FEC | FEC + NACK |
|---|---|---|---|
| 0% | inf | inf | inf |
| 2% | 47.15 | 61.56 | **inf** |
| 5% | 40.26 | 48.32 | **60.97** |
| 10% | 35.66 | 40.43 | **51.42** |
| 20% | 34.18 | 35.80 | **39.98** |
| 30% | 30.73 | 33.07 | **35.54** |

`inf` 表示输出码流与参考流**逐字节相同**。

### 结果：NAL 送达率（总 NAL 数 1811）

| 丢包率 | 无恢复 | 仅 FEC | FEC + NACK |
|---|---|---|---|
| 2% | 98.2% | 99.6% | **99.9%** |
| 5% | 94.4% | 98.9% | **99.7%** |
| 10% | 89.7% | 95.6% | **99.1%** |
| 20% | 80.5% | 85.5% | **95.1%** |
| 30% | 71.5% | 73.9% | **86.9%** |

### 结果：恢复机制的实际工作量

| 丢包率 | FEC 修复包数（仅 FEC） | FEC 修复 / NACK 请求（FEC+NACK） |
|---|---|---|
| 2% | 34 | 32 / 34 |
| 5% | 67 | 60 / 70 |
| 10% | 90 | 94 / 146 |
| 20% | 89 | 89 / 216 |
| 30% | 66 | 57 / 256 |

丢包率越高，NACK 请求增长越快而 FEC 修复数反而下降——因为 FEC 只能恢复"一组内恰好丢 1 个"的情况，丢 2 个以上就无能为力。这正是两者互补的地方。

### 结果：端到端延迟

所有档位的 p99 都稳定在 **69–70ms**，没有随丢包率恶化。说明：

- 延迟由帧保持窗口（60ms）主导，不是由恢复机制主导
- FEC/NACK 没有引入额外的排队延迟

延迟口径：**发送端采集完成 → 接收端把该帧写入文件**，不含解码与显示。加上解码（H.264 固有 1 帧延迟，约 33ms）与 UI 取帧（约 8ms）后，界面上的 p50 约 110ms（见实验三）。

## 实验二：抖动缓冲深度

### 方法

固定 5% 丢包，额外用 `tc netem delay 20ms 20ms` 注入 ±20ms 抖动。600 帧，每档 3 次重复取中位数。

两组配置：

- **固定**：保持窗口恒为 60ms
- **自适应**：`depth = clamp(20, max(k × jitter, rtt + margin), 120)`，抖动由 RFC 3550 公式估计

### 结果

| 场景 | 配置 | p50 | p99 | PSNR 中位 | 深度 |
|---|---|---|---|---|---|
| 无抖动 | 固定 60ms | 68.2 ms | 70.0 ms | **53.42 dB** | 60 |
| 无抖动 | 自适应 k=6 | **34.8 ms** | **36.6 ms** | 43.74 dB | 20 |
| 抖动 ±20ms | 固定 60ms | **69.6 ms** | **91.1 ms** | 37.98 dB | 60 |
| 抖动 ±20ms | 自适应 k=6 | 80.0 ms | 108.3 ms | **42.41 dB** | 52–75 |

**读法**：自适应不是"永远更好"，而是**跟着网络状况移动工作点**。

- 网络平稳时把窗口压到 20ms，延迟砍掉一半（68 → 35ms），代价是 9.7 dB 画质
- 抖动大时主动加深到 52–75ms，多花 10ms 延迟换来 4.4 dB 画质

### 一个反直觉的发现：k 值不能按直觉取

抖动 ±20ms 场景下扫描 `k`：

| k | 实测深度 | PSNR 中位 |
|---|---|---|
| 3（"3σ"直觉） | 31–39 ms | **29.84 dB** |
| 6 | 49–63 ms | **40.27 dB** |
| 8 | 82–107 ms | 38.02 dB |

`k=3` 比固定 60ms 低 9.9 dB。原因是 **RFC 3550 的 jitter 是被 1/16 平滑过的 EWMA 均值，天然低估峰值**，它用于 RTCP 上报是合适的，直接当缓冲深度用则偏小。当缓冲尺寸使用时要放大到 5–6 倍。

`k=8` 出现"NAL 更多但 PSNR 更低"的反常（3557 vs 3503 个 NAL，38.02 vs 40.27 dB），原因尚未查清，如实记录。

## 实验三：端到端延迟构成

同一份码流，对比两种消费方式：

| 环节 | 耗时 | 说明 |
|---|---|---|
| 帧保持窗口 | 60 ms | 配置值 |
| 收包 + 重组 + FEC/NACK | ~8 ms | 与无界面版本一致 |
| **H.264 解码固有延迟** | **~33 ms** | 解码器要等到下一个 AU 才开始输出上一帧 |
| UI 取帧等待 | 8.5 ms | 16ms 定时器 + 渲染占用 |

实测：无界面接收端 p50 = 68ms，UI 上屏 p50 = 110ms，差值 42ms 与上表的 33+8.5 吻合。

**这说明一帧的解码延迟是固定成本**，要压低总延迟只能减小保持窗口，代价是重传来不及（即实验二里的画质损失）。

## 实验四：拥塞控制

### 方法

用 `tc netem rate` 在 `lo` 上造带宽瓶颈，接收端加 `--feedback` 回传时序样本，发送端加 `--cc` 按估计结果调整编码码率。600 帧（20 秒内容），1.2 Mbit 链路，起始码率 1400 kbps。

**必须先说明内容熵的问题**。彩条画面太平坦，x264 无论目标码率设多少都会贴着 QP 上限输出，这时码率控制环控制的变量对实际输出**没有影响**，测出来的"自适应"是假的。实测：

| 目标码率 | 无噪声的实际输出 | 噪声幅度 60 时的实际输出 |
|---|---|---|
| 200 kbps | — | 240 kbps |
| 500 kbps | — | 496 kbps |
| 1000 kbps | — | 1000 kbps |
| 2000 kbps | **59 kbps** | 2128 kbps |

所以实验统一加 `--noise 60`，让编码器真正吃满目标码率。

### 结果：开与不开的对比

| | 关闭拥塞控制（固定 1400 kbps） | 开启拥塞控制 |
|---|---|---|
| 码率调整次数 | 0 | 12 |
| 接收端耗时 | 27.60 s | **20.98 s** |
| 累积排队延迟 | 7.6 s | **≈1 s** |
| 送达 NAL | 3525 | **3663** |
| 平均接收码率 | 1105 kbps（跑满链路） | 840 kbps |
| 末窗队列延迟 | 持续增长 | **0.5–1.6 ms** |
| 末态 | 一直过载 | `normal`，800–950 kbps |

发送端固定发 1400 kbps 打 1200 kbit 的链路，多出来的部分全部堆在队列里，20 秒的内容收了 27.6 秒。开启拥塞控制后降到 840 kbps 左右，队列被排空，接收耗时回到接近实时。

### 结果：码率轨迹（AIMD 锯齿）

```
1400 → 1190                 降（已接近链路容量 1200）
     →  860 → 621 → 324     继续降，触底
     →  350 → 408 → 476
     →  556 → 648 → 756
     →  882                 加性提速，爬过可用带宽
     →  688                 再次检测到过载，回降
```

（日志按 1 秒节流，个别中间值未打印）

读法：

1. 前 4 次降速是**起步过冲**的代价——起始 1400 已经高于 1200 的链路容量，队列迅速堆积，检测器连续判过载
2. 触底 324 后进入加性提速，每个窗口 ×1.08，用 7 次调整爬回 880
3. 880 kbps 的**载荷**加上 FEC 的 1/8 开销已经接近 1200 kbit 链路的实际承载上限，于是再次被判过载，回落到 688
4. 最终在 **800–950 kbps** 之间摆动，约为链路容量的 **65%–80%**

70% 左右是加法提速 + 过冲即降的固有代价，不是缺陷：要更高的链路利用率就得承受更频繁的排队。也因为它是锯齿，**单次读到的稳定值没有意义**——重复两次实验分别得到 803 与 944 kbps，差异完全来自采样时刻，而两次的接收耗时（20.98s / 20.99s）几乎相同。

### 踩坑一：`x264_encoder_reconfig` 改码率无效

第一次跑实验时，码率明明已经降到 300 kbps，链路却始终饱和、积压 8 秒。追查发现：

```
目标 2000 kbps → 实际 2128 kbps        离线编码，跟随目标，正常
重配到 300 kbps 后的 40 帧: 481437 字节
重配前            40 帧: 474094 字节   ← 反而变大了
```

**本机 x264 164 上 `x264_encoder_reconfig` 修改 `rc.i_bitrate` 完全不生效。**

更值得注意的是：原有的测试是这么写的——

```cpp
ASSERT_TRUE(encoder->set_bitrate(400, &error));
EXPECT_EQ(encoder->bitrate_kbps(), 400);   // 只验证了"自己记住了"
```

它验证的是返回值和内部状态，**不是实际输出**，所以这个 bug 一直藏着。现在换成了用高熵内容比较重配前后真实字节数的测试（`RuntimeBitrateReconfigActuallyChangesOutput`）。

修复方式：`set_bitrate` 改为重建编码器（`open()` 内部会先 `close()`，是安全的），代价是重新输出一次 SPS/PPS + IDR。

### 踩坑二：降速策略必须有的两个补丁

| 问题 | 现象 | 修复 |
|---|---|---|
| 连续下调 | 大过冲后队列要几秒才排空，期间检测器仍看到正值延迟，于是一路降到底（1 Mbit 链路被压到 200 kbps 下限） | 降速冷却 250 ms |
| 单次砍太狠 | 按严重度分 4 档、一次砍掉 48%：1190 → 621 → 324 → 300 | 最多 2 档（一次 ≤28%） |

这两个补丁都是先被实验打脸、再补上的，单看代码很难想到。

### 局限

- 只在 loopback 上用 `netem rate` 测过，**没有真实跨机链路数据**
- 单流，没有交叉流量，也没有测链路容量中途变化的响应速度
- 延迟梯度依赖两端时钟同源（本项目同主机 `CLOCK_MONOTONIC`），跨机需要时钟频率一致
- 反馈周期固定 300 ms，链路突变时反应偏慢

## 已知局限

1. **netem 加在 `lo` 上双向生效**，比真实单向丢包更严苛，因此本文的丢包率可以理解为"双向各半"的合计
2. **每档只有 2 次重复**（实验二为 3 次），PSNR 方差较大，表中为算术平均/中位数
3. **PSNR 是逐帧对齐比对**。如果某次运行恰好丢失第一帧，整段帧序会错位，PSNR 会被低估；这类样本没有剔除
4. **没有记录 CPU 与内存占用**，"恢复机制的开销是多少"目前无数据
5. 带宽瓶颈只测了单一固定档位（实验四），没有做 `rate` 的档位扫描，也没有测容量动态变化的场景

## 复现

```bash
# 实验一
./scripts/bench.sh

# 实验二（固定 vs 自适应）
./scripts/jitter_test.sh --mode fixed    --delay "20ms 20ms" --loss 5 --frames 600
./scripts/jitter_test.sh --mode adaptive --delay "20ms 20ms" --loss 5 --frames 600 --k 6

# 实验四（拥塞控制）：1200 kbit 链路 + 高熵内容
unshare -rn sh -c '
  ip link set lo up
  tc qdisc replace dev lo root netem rate 1200kbit
  ./build/src/app/lowlat_receiver --bind 127.0.0.1:5986 --output out/cc.h264 \
      --frames 600 --duration 60 --nack --feedback &
  sleep 1
  ./build/src/app/lowlat_sender --frames 600 --dest 127.0.0.1:5986 --fec --cc \
      --bitrate 1400 --min-bitrate 300 --max-bitrate 2500 --noise 60
'
# 去掉 sender 的 --cc 即为对照组
```
